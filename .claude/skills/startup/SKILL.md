# Открытие сессии

Ты открываешь сессию. Задача: за несколько секунд дать владельцу понятную
картину состояния проекта и, если предыдущая сессия оставила блокер, снять
его до любой другой работы.

Процедура описана здесь целиком, своего convention у неё нет: это поведение
агента, а не правило о проекте. Содержательные правила, по которым ты ходишь:
`CLAUDE.md` → «Порядок чтения», `spec-program` → «Вход в работу»,
`context/workflow.md` → `report`, `goals` → «Отчёт по статусу»; формат
`context/main.md` — в шапке самого файла.

Зачем процедура нужна, если порядок чтения и так записан: она делает проход
принудительным и одинаковым в каждой сессии, ставит машинный чек до начала
работы, а не в конце, и втягивает в срез состояние git — шаг, который легко
пропустить.

## Границы роли

- **Не читаешь слои `docs/`** — они читаются под конкретную задачу.
- **Не ходишь в сеть** — ни сверка с источниками, ни версии игры.
- **Не запускаешь `npm run check`** целиком: typecheck и тесты превращают
  быстрый чек в ожидание.
- **Не правишь файлы** помимо резолва записи `[blocker]`.
- **Не берёшь работу сам** — сводка кончается предложением, выбор за
  владельцем.

## Шаг 1. `context/main.md` и выбор ветки

Читаешь его первым, до всего остального: от содержимого зависит, нужна ли
сводка вообще.

- **есть `[blocker]`** → сводку не печатаешь. Предъявляешь запись и сразу
  идёшь в резолв: вызов скилла и есть мандат на выполнение, подтверждения не
  ждёшь. Запись требует решения владельца — выполнять нечего, задаёшь вопрос
  первым сообщением по формату `context/workflow.md` → «Формат блокирующего
  вопроса». Сказали «потом» — печатаешь сводку, запись в ней остаётся
  видимой;
- **непуст, но без `[blocker]`** → сводка целиком, и строка «первым» —
  добить записи `main.md`;
- **пуст** → обычная сводка.

Записи, закрытые по ходу резолва, удаляются только вместе с переносом знания
в целевой артефакт — то же требование, что у скилла `closeout`.

## Шаг 2. Собрать состояние

```bash
git status --short
git diff --stat
git diff --cached --stat
```

Затем по файлам:

- `context/views/goals.yaml` и `program--*.yaml` — что в работе, порядок
  записи = приоритет;
- последний `plans/<key>/iter-NN.html` — статус, номер итерации и горизонт
  из `<meta name="plan-*">`, не из видимого текста;
- последний вердикт `.work/plan-review/<key>/iter-NN--verify-MM.md` —
  `changes-requested` означает, что подцели в работу не берутся;
- `.work/review/<goal-key>/` — открытые раунды;
- `.work/proofs/<program-key>/` — какие пруфы уже сняты, каких ждут от
  владельца;
- `sync.contract.synced_at` в `context/project.yml` — старше 14 дней даёт
  одну строку с предложением прогнать сверку. Сверку сам не запускаешь.

Следующая подцель определяется алгоритмом «вход в работу» из `spec-program`,
а не памятью и не порядком файлов на диске.

## Шаг 3. Проверки

```bash
npm run check-docs
npm run check-secrets
```

Вместе меньше секунды. Красное — строка в блоке «проверки» с сутью ошибки.
Чинить на старте не обязан: решает владелец, но находку прячешь.

## Шаг 4. Сводка

Каркас фиксированный, порядок блоков не меняется, **пустой блок опускается
целиком**. Сырые YAML не пересказываешь, процесс не объясняешь.

```
main.md       2 записи: 1 high, 1 low
в разработке  <программа> — <стадия>, итерация NN [ТЕГ]: <горизонт одной строкой>
можно взять   <цель> — <что в ней>
незакончено   застейжено N файлов — ждёт /review
проверки      check-docs ок · check-secrets ок · sync 3 дня
первым        <одна строка>
```

Чистое состояние — три-четыре строки, и это нормальный результат, а не
признак, что ты чего-то не посмотрел. Пустые `mods/` и `poc/` при живой
программе на стадии PoC в сводку не попадают: это норма, не находка.
