# Закрытие сессии

Ты закрываешь сессию. Задача одна: **быстро свернуться, не потеряв
существенного.** Знание, выясненное в диалоге и не попавшее в файлы, исчезает
вместе с контекстом — ты последний, кто может его записать.

Процедура описана здесь целиком, своего convention у неё нет: это поведение
агента, а не правило о проекте. Содержательные правила, по которым ты ходишь:
`openness` (куда идёт проектный факт), `goals` (задачи и приоритеты),
`engine-facts` (факты о движке), `verification` (`verified`), `secrets`,
`spec-program` (пруфы, ревью); формат `context/main.md` — в шапке самого файла.

Процедура не аудит: полный прогон по состоянию проекта — сценарий `audit` в
`context/workflow.md`, смешивать их незачем.

Вызов скилла владельцем — мандат на правку файлов. Отдельного согласования
списка выносов до работы нет: второй раунд диалога противоречит смыслу
процедуры. Всё идёт в один отчёт в конце.

## Границы роли

- **Не доделываешь работу.** Незавершённая подцель остаётся незавершённой;
  ты выносишь знание, а не дописываешь код.
- **Не делаешь `git add`** и не трогаешь индекс git: застейженная подцель
  ждёт `/review`.
- **Не ставишь `verified: true`** без свежей проверки.
- **Не предлагаешь очистку** `.work/`, `poc/` и решённых целей.
- **Не запускаешь `/review`**, не закрываешь цели, не меняешь `stage`
  программы.
- **Чужие записи в `main.md` не удаляешь.** Оставленное предыдущей сессией и
  не разобранное в этой остаётся на месте и попадает в отчёт.

## Шаг 1. На что опираешься

Память о диалоге — не единственный источник: контекст мог быть суммаризован,
и тогда часть сессии ты не помнишь. Собери наблюдаемое:

```bash
git status --short
git diff --stat
git diff --cached --stat
```

Плюс `context/main.md`, содержимое `.work/` по активной программе и свежие
правки файлов. Если контекст сжимался — скажи это в отчёте одной строкой:
полнота не гарантирована.

## Шаг 2. Инвентаризация

Пройди чек-лист категорий и выпиши, что в этой сессии появилось и не
записано:

1. решение владельца под критерий журнала — нет строки в `CHANGELOG.md`;
2. особенность движка — не доехала до namespace `engine`;
3. наблюдение или дефект — нет задачи в цели;
4. устойчивая договорённость о работе — нет записи в convention;
5. отброшенная альтернатива и причина отказа;
6. вопрос, на который нужен ответ владельца;
7. снятый пруф, не привязанный к пункту `dod`;
8. красная машинная проверка без разбора.

Пусто по всем восьми — так и скажи, процедура на этом не заканчивается:
шаг 4 обязателен всё равно.

## Шаг 3. Разложить и записать

По каждой находке — один из трёх адресов:

- **устойчивое** → слой: `docs/entities/`, `docs/behavior/`,
  `docs/manuals/`, `context/conventions/`, `context/project.yml`,
  `CHANGELOG.md`;
- **определённая работа** → задача в подходящую цель `context/views/`,
  в секцию по приоритету;
- **остальное** → `context/main.md`.

Граница между задачей и слоем формальная, не на вкус: суть влезает в строку
задачи (~200 символов) — задача; не влезает — устойчивый факт, и он пишется в
слой целиком. Огрызок behavior или факт `engine` без версии игры `check-docs`
не пропустит, и это правильно.

Запись в `main.md` — в раздел по приоритету (`[blocker]`, `[high]`,
`[medium]`, `[low]`); раздел создаётся только вместе с первой записью.
`[blocker]` — когда без ответа владельца нельзя двигаться дальше, в том числе
для сложного вопроса, который не разобрать в хвосте уходящей сессии.

Чего в `main.md` **не бывает**: выводимого из файлов — следующая подцель,
статус программы, прогресс по задачам (состояние выводится, а не хранится,
`spec-program` → «Вход в работу», и дубль начнёт врать на первой же правке);
и устойчивого знания — факт, договорённость, решение едут в свои слои,
`main.md` не черновик документации и не журнал.

Раздел жив, только пока в нём есть записи: обработана последняя — заголовок
уходит вместе с ней. Это обратно правилу для целей, где пустые секции
сохраняются, и причина в носителе: вся ценность `main.md` — в бинарном
сигнале «пусто / не пусто», который следующая сессия снимает на старте, а
пустые заголовки делают файл заполненным на вид. Идеальное состояние — без
разделов вовсе, под шапкой строка «Записей нет.»: она отличает пустой файл от
обрезанного.

```markdown
[blocker]

- 2026-10-04 · <суть одной строкой>
  требуется: <что и от кого — решение владельца, прогон в игре, доступ>
  известно: <что уже выяснено, чтобы не открывать вопрос заново>
  привязка: программа logistic-buildings | цель toolchain | вне программы
  переедет: <куда знание уйдёт после закрытия записи>
```

Записи этой сессии, которые по ходу разрешились, удаляй — но **только
одновременно с переносом** в целевой артефакт, и назови в отчёте, куда.
Удалить, ничего не перенеся, — та же потеря, от которой заведён файл.

Файл версионируется: ни абсолютных путей с именем пользователя, ни ключей —
`secrets`.

## Шаг 4. Проверки

```bash
npm run check-secrets
npm run check-docs
```

- `check-secrets` **должен быть зелёным** — это абсолютное условие
  завершения. Находка правится немедленно, здесь же, до отчёта;
- `check-docs` красный завершению не мешает. Разбери, если это поломка от
  правок этой сессии и починка короткая; иначе — запись в `main.md` с
  приоритетом и точным текстом ошибки. Условием закрытия его делать нельзя и
  технически: тогда незакрытая запись в `main.md` запирала бы сессию, которая
  эту запись и создала.

## Шаг 5. Отчёт

Одно сообщение, без пересказа процедуры:

- вынесено: по строке на находку — что и куда (файл);
- `main.md`: сколько записей добавлено, сколько осталось с прошлых сессий,
  есть ли `[blocker]`;
- проверки: `check-secrets` — ок; `check-docs` — ок либо что красное и куда
  записано;
- затронутые файлы списком — владельцу надо отделить выносы знания от
  незавершённой работы, когда он будет коммитить;
- блокирующие вопросы — единым блоком по формату из `context/workflow.md`,
  если они есть.

Потерь не нашлось — отчёт в три строки: искал по восьми категориям, пусто,
проверки зелёные.
