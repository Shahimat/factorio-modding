# CLAUDE.md

Точка входа агента. Только маршрутизация — содержательное живёт в слоях.

Проект работает по операционному контракту `agent-operational-contract-v2`.
Сам контракт в репозитории не лежит — он внешний, его raw-URL и SHA-256
записаны в `context/project.yml` → `sync`. Ключевые его правила перенесены в
`context/workflow.md` и `context/conventions/` (`verification`, `goals`,
`goal-consistency`, `openness`). Если нужен полный текст контракта —
вытащи его по `sync.index_source`, строго `curl`, протокол в
`context/workflow.md` → «Синхронизация с источниками».

## Порядок чтения

1. `context/project.yml` — реквизиты, namespaces, блок `sync`.
2. `context/index.yml` — карта репозитория, отсюда выбираешь конкретные файлы.
3. `context/modules/*.yml` — подключённые модули расширения (сейчас ни одного).
4. `context/workflow.md` — протоколы сценариев `plan` / `execute` / `audit` /
   `challenge` / `report`.
5. Релевантные `context/conventions/*.yml` по ключам задачи.
6. Релевантные `docs/entities/*.yml` и `docs/behavior/*.yml` по namespace.
7. `docs/manuals/*.md` — только для процедурных задач.
8. `context/views/goals.yaml` (+ нужные `goal--*.yaml`) — только когда нужен
   рабочий срез очереди.

`README.md` — точка входа для человека, читай по необходимости.
`CHANGELOG.md` — журнал решений, читай по запросу «когда» / «почему», не для
ответа на «как сейчас».
## Скиллы

- `/plan-spec` — разложить ТЗ из `specs/` по слоям, согласовать с владельцем
  план программы в `plans/` и только после «согласовано» завести
  программу с подцелями и DoD.
- `/verify-plan` — сверить заведённые цели с согласованным планом. Отдельный
  контекст: автозапуск подагентом в конце `/plan-spec`, повторный прогон —
  руками.
- `/review` — проверить застейженную подцель против её DoD. Запускается в
  свежей сессии, не в сессии исполнителя.

Скиллы процедурны: правила живут в `context/conventions/`, скилл только ведёт
по ним. Полный список — `context/index.yml` → `skills`.

`plans/` — согласованные планы итераций, по HTML на итерацию; версионируются,
правила — `context/conventions/spec-program.yml`, раздел «План программы».
`specs/` — входящие ТЗ от автора, правила обращения — в
`context/conventions/spec-intake.yml`, а порядок работы по ним (программа,
DoD, пруфы, ревью) — в `context/conventions/spec-program.yml`.
`.work/` — пруфы и раунды ревью, вне git, срок жизни и очистка там же.

## Жёсткие правила

- **Репозиторий публичный. Ничего чувствительного и приватного в
  версионируемые файлы — никогда, ни в каком виде, ни «временно».** Ключи,
  токены, личные адреса, абсолютные пути с именем пользователя. Правило и
  белые списки — `context/conventions/secrets.yml`, проверка —
  `npm run check-secrets`.
- Перед любым `plan` и перед любой правкой — сначала прочитай документацию по
  релевантному namespace. Правка без чтения — нарушение контракта.
- `verified: true` живёт только в `docs/behavior/*.yml`, ставится по свежей
  проверке, см. `context/conventions/verification.yml`.
- Устойчивые уточнения — в репозиторий, не в memory и не в hooks. «Запомни» =
  правка проектной документации. См. `context/conventions/openness.yml`.
- Сложная задача идёт атомарными фазами по типу коммита
  (`docs` → `fix` → `refactor` → `feat`), смешивать типы в одной фазе нельзя.
  Исключение — подцель программы по спеке: порядок фаз сохраняется, но точка
  согласования одна, на всю подцель, а контроль переносится на ревью. См.
  `context/conventions/spec-program.yml` и отклонение
  `spec-program-granularity` в `context/project.yml`.
- Крупные решения фиксируются одной строкой в `CHANGELOG.md` в фазе `docs`.
