# Техническое задание: мод «Логистические здания» для Factorio

Рабочее название: **Logistic Buildings** (внутреннее имя `logistic-buildings`). Название предварительное, владелец может его заменить.

Этот документ — постановка задачи для исполнителя, который будет писать мод. Все решения по дизайну уже приняты и описаны ниже вместе с причинами. Причины даны для того, чтобы в ситуациях, которые документ не покрывает, можно было принять решение в духе замысла.

---

## 1. Замысел

В обычной Factorio любое производящее здание подключается к логистической сети через связку «сундук запроса → манипулятор → здание → манипулятор → сундук снабжения». Мод убирает эту обвязку: **любое здание можно переключить в логистический режим, и оно само становится участником логистической сети** — запрашивает ингредиенты и отдаёт продукцию дронам напрямую.

Цель владельца — «город без манипуляторов»: база, где здания стоят отдельно, а всё перемещение делают дроны по запросам.

Три свойства, которые отличают мод от существующих аналогов (Logistic Assembling Machine, Logistic Machines):

1. **Режим на любом здании**, а не отдельные «логистические версии» машин. Работает с машинами любых модов без кода под конкретный мод.
2. **Производство по спросу.** Здание не производит бесконечно: оно работает, только пока в сети есть неудовлетворённые запросы на его продукцию.
3. **Пакетная доставка.** Ингредиенты заказываются и продукция отгружается партиями, чтобы дроны летали с полной загрузкой, а не с парой предметов.

## 2. Рамки

### 2.1. Версии игры

- Нужны **два релиза из одной кодовой базы**: под Factorio 2.0 и под Factorio 2.1. Один архив мода работает только с одной версией игры.
- Сначала разработка и проверка на **2.0** (владелец сейчас играет на ней), затем перенос на 2.1.
- Все обращения к API, которые различаются между версиями, проходят через один файл-прослойку.
- Список изменений API 2.1 при подготовке документа не проверялся. Брать его нужно из официальной документации (lua-api.factorio.com), а не из неофициальных гайдов.

### 2.2. Зависимости и совместимость

- Жёсткая зависимость только от `base`. Мод обязан запускаться на чистой игре без DLC.
- Мод должен корректно работать вместе с: Space Age, Quality, Elevated Rails, Krastorio 2, модами планет (владелец назвал пак «PlanetsLite»; предположительно это «Enable Planet Mods Lite», `kry-planet-mods-lite`), в частности Cerys.
- Главное правило совместимости: **ничего не определять по именам прототипов**. Здания, дроны, технологии, топливо, патроны, колбы — всё находится по типу и свойствам прототипа. Тогда содержимое любых модов подхватывается само.
- Качество учитывается всегда. В движке оно существует и без DLC (одно, «обычное»), поэтому отдельной ветки кода для игры без Quality быть не должно: ключ любого учёта — пара «предмет + качество».
- Каждая поверхность (планета) имеет свои логистические сети. Весь учёт ведётся отдельно по каждой сети. На поверхностях без дронов (космические платформы) режим просто ничего не делает и не выдаёт ошибок.
- В настройках нужен список исключений: имена сущностей, на которых режим недоступен (для машин, которые другие моды сами обвешивают скриптами).

### 2.3. Что входит в первую версию

- Производящие машины: сборочные автоматы, печи и всё того же класса (химзаводы, литейные, биокамеры и т. д.).
- Лаборатории (режим «только запрос»).
- Буры, добывающие твёрдые ресурсы (режим «только выдача»).
- Заправка твёрдым топливом любых зданий с топкой, включая здания, которым нужно только топливо (котлы, реакторы, нагревательные башни).
- Турели на патронах (за флагом настройки, по умолчанию выключено).
- Сельскохозяйственная башня (за флагом настройки, по умолчанию выключено).
- Ракетная шахта (за флагом настройки, по умолчанию выключено).
- Настройки вместимости дронов.
- Производство по спросу, пакетный заказ и отгрузка, режим «работа по избытку».

### 2.4. Что не входит

- Транспорт (машины, танки, локомотивы, паукотроны).
- Перевозка жидкостей дронами. Жидкости здания получают и отдают по трубам, как в ваниле.
- Нефтяные вышки и любые буры с жидким продуктом.
- Груз ракеты (его доставку оставляем ванильной механике).
- Отдельная технология и отдельные «логистические версии» зданий.
- Собственная графика.

## 3. Принятые решения и причины

| Решение | Причина |
|---|---|
| Режим включается на существующем здании, новых прототипов зданий нет | Копии зданий удваивают меню крафта и ломаются на чужих модах (цепочки улучшений, скрипты других модов, списки модулей) |
| Включение режима бесплатное | Комплект переоборудования усложняет постройку по чертежам; владелец выбрал простоту |
| Своей технологии нет; доступность определяется по открытым рецептам сундуков | Имена технологий в оверхолах меняются; проверка «открыт ли рецепт сундука» работает везде |
| Скрытых манипуляторов нет, предметы перекладывает скрипт | Убирает две сущности на здание и проблему наведения манипулятора на перекрывающиеся сущности |
| Скрипт работает партиями по «будильнику», а не опросом | Нагрузка определяется числом партий в секунду, а не числом зданий |
| Целей производства как отдельного интерфейса нет; цель выводится из запросов сундуков сети | Игрок управляет запасом привычным способом (буферный сундук), рисовать окно не нужно |
| Вход настраивается по каждому ингредиенту, выход — по каждому продукту | Даёт гибриды с конвейерами и решает проблему побочных продуктов |
| Выход по умолчанию пассивный | Продукт не едет дважды (здание → склад → потребитель) |
| Жидкости только по трубам | Тара для жидкостей отложена на будущее (раздел 14) |
| Топливо, патроны и семена по умолчанию доставляются через ванильные «призраки запроса предмета», а не через скрытый сундук | Турелям, котлам и реакторам не нужны скрытые сундуки; доставку делают строительные дроны, у которых зона действия больше логистической; игрок видит штатный значок запроса |
| Для топлива и семян способ доставки переключается в панели здания: строительные дроны (по умолчанию) или логистические | При большом расходе строительные дроны не справляются: они несут мало и не возят партиями |

## 4. Модель здания

### 4.1. Входы и выходы

У здания в логистическом режиме для каждого входа и выхода задано, кто его обслуживает.

| Что | Варианты | По умолчанию |
|---|---|---|
| Каждый твёрдый ингредиент рецепта | из сети (дроны) / внешний (манипулятор кладёт сам) | из сети |
| Жидкие ингредиенты и продукты | всегда внешние (трубы) | — |
| Топливо (если у здания есть топка) | из сети / внешнее | внешнее, пока игрок не выбрал вид топлива |
| Патроны (турели) | из сети / внешние | внешние, пока игрок не выбрал вид патронов |
| Семена (сельскохозяйственная башня) | из сети / внешние | внешние, пока игрок не выбрал вид семян |
| Основной продукт рецепта | пассивное снабжение / активное снабжение / локально | пассивное |
| Остальные продукты рецепта | те же три | активное |
| Продукт «не того» качества (от модулей качества) | те же три | активное |

Пояснения:

- **Внешний вход** означает, что мод этот предмет не запрашивает и не учитывает в расчёте запаса. Его приносит обычный манипулятор, поставленный игроком.
- **Локальный выход** означает, что продукт остаётся в выходном слоте здания, откуда его забирает обычный манипулятор. Мод его не трогает.
- Если манипулятор приносит ингредиент, который не снят с запроса, это безвредно: скрипт видит предмет в машине и заказывает меньше.
- Здание, у которого все входы внешние, а выход в сеть (например, печи на конвейере, отдающие плиты дронам), — штатный сценарий. Обратный (всё из сети, продукт на конвейер) — тоже.

### 4.2. Скрытые сундуки

Здание подключается к сети через скрытые логистические сундуки, которые мод создаёт в центре здания:

- **сундук запроса** — если из сети идёт хотя бы один ингредиент рецепта или колбы лаборатории, а также если топливо или семена переведены на доставку логистическими дронами (см. 4.5);
- **сундук пассивного снабжения** — если хотя бы один продукт выходит пассивно;
- **сундук активного снабжения** — если хотя бы один продукт выходит активно, а также как выход для «мусора» (см. 9.3). Он нужен и при локальном выходе, если есть сундук запроса.

Требования к прототипам сундуков (их три: запрос, пассивный, активный):

- около 50 слотов, чтобы помещалась партия по всем ингредиентам и топливо;
- без коллизии, чтобы внешние манипуляторы рядом со зданием наводились на само здание, а не на сундук;
- не выделяются мышью, не попадают в чертежи, планы сноса и замены, не являются целью для врагов, неразрушимы, скрыты из списков;
- у сундука запроса включено «запрашивать из буферных сундуков» — иначе запас, который игрок держит в буферах, до зданий не дойдёт.

Сундуки создаются только когда нужны и удаляются, когда перестают быть нужны. При смене режима продукта с пассивного на активный содержимое переносится между сундуками.

### 4.3. Типы зданий

| Тип | Что делает мод | Особенности |
|---|---|---|
| Производящие машины с выбором рецепта | Запрос ингредиентов, отгрузка продуктов, топливо | Полная модель из 4.1 |
| Печи (рецепт выбирается автоматически) | То же | В панели поле «что производить»: мод должен знать рецепт, чтобы запрашивать ингредиенты. Список — рецепты из категорий этой печи |
| Лаборатории | Только запрос колб | Запрашиваются колбы текущего исследования из тех, что принимает лаборатория. Набор обновляется по событиям смены исследования. Нет исследования — запросов нет |
| Буры (твёрдый продукт) | Только выдача | Бур сам сбрасывает руду в скрытый сундук (сундук назначается целью сброса). По умолчанию пассивный. Размер буфера задаётся ограничением слотов сундука. Бур встаёт сам, когда сундук заполнен, — скрипт в работе не участвует |
| Здания только с топкой (котлы, реакторы, нагревательные башни) | Только топливо | По умолчанию скрытых сундуков нет: топливо доставляется призраком запроса, отработанное вывозится запросом на изъятие. Если доставка переключена на логистических дронов, у здания появляются скрытые сундуки (см. 4.5) |
| Турели на патронах, артиллерия | Только патроны | Скрытых сундуков нет, патроны доставляются призраком запроса. Расход непредсказуем, поэтому медленный опрос вместо будильника (см. 6.5). За флагом настройки |
| Сельскохозяйственная башня | Семена на вход, урожай на выход | Вид семян выбирает игрок. Семена доставляются призраком запроса или, по переключателю, логистическими дронами (см. 4.5) и запрашиваются, только пока есть спрос на урожай (продукт определяется по растению, которое вырастает из семени). Урожай скрипт перекладывает в сундук снабжения. Медленный опрос, как у турелей. За флагом настройки |
| Ракетная шахта | Только запрос ингредиентов деталей ракеты | Рецепт у шахты фиксированный. Ингредиенты идут через сундук запроса обычным циклом партии. Проверки спроса нет: шахта сама перестаёт потреблять, когда ракета собрана. Груз ракеты мод не трогает. Если после запуска в шахте появляется результат (игра без Space Age), он отгружается как продукт. За флагом настройки |

Топливо и патроны определяются универсально: по наличию у сущности топки или инвентаря патронов и по допустимым категориям. Вид топлива или патронов выбирает игрок в панели из допустимых для этого здания. Автовыбора «лучшего из доступного» нет: поведение должно быть предсказуемым.

Это относится и к зданиям модов. Владелец отдельно назвал башни на твёрдом топливе из мода Cerys: кода под них быть не должно, они должны подхватиться по наличию топки, и на них нужно проверить заправку (раздел 13).

Питательные вещества биокамеры для движка — обычное топливо, отдельной логики для них не нужно.

### 4.4. Доступность режима

Отдельной технологии нет. Возможности открываются вместе с ванильными сундуками:

- игроку открыт рецепт сундука пассивного снабжения → доступны режимы выдачи (буры, пассивный выход);
- открыты рецепты сундука запроса и сундука активного снабжения → доступны запросы и активный выход.

Проверять нужно именно открытость рецепта предмета, который ставит логистический контейнер соответствующего типа, а не название технологии.

### 4.5. Топливо, патроны и семена: призраки запроса

В игре есть штатная сущность «призрак запроса предмета» (item request proxy): она привязывается к зданию, перечисляет, какие предметы в какой слот положить, и её выполняют **строительные** дроны. Игрок пользуется ею, когда удалённо заказывает модули или топливо в здание. Мод использует её для расходников, которые в здании только убывают.

**Способ доставки:**

| Расходник | Способ |
|---|---|
| Патроны | всегда строительные дроны (призрак запроса) |
| Топливо | переключатель в панели здания: строительные дроны (по умолчанию) / логистические дроны |
| Семена | такой же переключатель, по умолчанию строительные дроны |
| Ингредиенты рецептов, колбы | всегда логистические дроны (сундук запроса) |

Переключатель задаётся на каждом здании отдельно для топлива и для семян, сохраняется в чертежах и копируется вместе с остальными настройками (7.4).

**Доставка логистическими дронами** нужна при большом расходе: биокамера сжигает питательные вещества за секунды, а строительный дрон без переопределения вместимости несёт 1–4 предмета и не возит партиями. В этом режиме:

1. Топливо или семена запрашиваются скрытым сундуком запроса как ещё одна строка, с теми же порогом и партией. Если сундука у здания ещё нет, он создаётся.
2. Скрипт перекладывает их из сундука в топливный инвентарь или инвентарь семян при посещении здания.
3. Расход топлива известен, поэтому будильник ставится на момент, когда запас в топке упадёт до порога. Если расход рассчитать нельзя, здание проверяется медленным опросом, как турели.
4. Отработанное топливо уходит в сундук активного снабжения (создаётся при необходимости).
5. Спрос учитывается как у любого скрытого сундука мода (5.1).

Ограничение: здание должно стоять в логистической зоне робопорта, которая меньше строительной.

При смене способа на работающем здании ничего не должно теряться и заказываться дважды: мод снимает из призрака только свои невыполненные строки, а остаток из сундука запроса догружает в здание или отправляет как мусор (9.3).

**Доставка строительными дронами:**

1. При проверке здания скрипт считает: «лежит в инвентаре + уже заказано призраком». Если это меньше порога, он дозаказывает до размера партии.
2. Если на здании уже есть призрак запроса (от игрока или из чертежа, например на модули), заказ мода добавляется в него. Чужие строки не затираются, второй призрак с теми же предметами не создаётся.
3. Строительные дроны кладут предметы прямо в нужный слот. Скрипт в доставке не участвует.
4. Отработанное топливо у зданий без сундука активного снабжения вывозится запросом на изъятие в том же призраке.

**Учёт спроса.** Призрак не является точкой запроса логистической сети, поэтому сам по себе производство не запускает. Мод ведёт реестр своих призраков и добавляет недостающее по ним количество в цели сети (см. 5.1).

**Что нужно иметь в виду:**

- Зона строительных дронов у робопорта больше логистической. Турели и котлы на краю базы обслуживаются там, куда логистические дроны не долетают.
- Доставить может и личный робопорт игрока из его инвентаря, если игрок рядом. Это штатное поведение призраков.
- При вместимости строительных дронов 1–4 стак патронов — это десятки рейсов. Для баз с большим расходом стоит включать переопределение вместимости строительных дронов или уменьшать партию. Топливо и семена проще перевести на логистических дронов.
- Если предмета в сети нет, игра может показывать предупреждение о нехватке материалов для строительства. Нужно проверить, не превращается ли это в спам (раздел 11).

## 5. Спрос: когда здание работает

### 5.1. Правило

Для каждой логистической сети и каждой пары «предмет + качество» считаются две величины:

- **Запас** — сколько предмета доступно в сети (сундуки снабжения, хранения и буферные).
- **Цель** — сумма по всем точкам запроса сети:
  - для **буферных сундуков** — запрос целиком;
  - для **остальных точек запроса** (сундуки запроса, персонажи игроков и т. д.) — только недостающее: `max(0, запрос − уже лежит − везут дроны)`;
  - для **скрытых сундуков самого мода** — недостающее по текущему заказу партии;
  - для **призраков запроса, созданных модом** (4.5) — недостающее по ним количество.

Производитель работает, пока по хотя бы одному его продукту **запас < цель**.

Почему буферные и обычные сундуки считаются по-разному: содержимое буферного сундука входит в запас сети, а содержимое сундука запроса — нет. Если считать сундук запроса целиком, после доставки запас снова окажется ниже цели и здания произведут лишнюю партию.

### 5.2. Что из этого следует

- **Промежуточные продукты заказываются сами.** Заказ партии шестерёнок скрытым сундуком сборщика становится целью для производителей шестерёнок, и так вниз по цепочке до буров.
- **Буферный сундук — способ держать запас.** Без буферов всё производится строго под заказ, и каждая партия ждёт всю цепочку. Буферный сундук с запросом на 500 шестерёнок заставляет сеть держать 500 шестерёнок, и заказы обслуживаются из запаса.
- **Запросы игрока** учитываются автоматически.
- **Излишки на складе** считаются запасом: пока они не израсходованы, производители этого предмета спят.
- Призраки строительства и чужие призраки запроса предметов точками запроса не являются и на производство не влияют. Свои призраки мод учитывает сам.

### 5.3. Качество в запросах

- Запрос с точным качеством учитывается по этому качеству.
- Запрос с условием («редкое и выше», «любое»): запасом считается сумма всех подходящих качеств; работают все производители, чьё качество продукта подходит под условие.
- Скрытый сундук здания запрашивает ингредиенты того же качества, что выбрано в рецепте.

### 5.4. Работа по избытку

Второй вариант условия запуска, включается флагом в панели здания. Здание запускается не по спросу на продукт, а когда **выбранного ингредиента в сети больше заданного порога**. Нужен для утилизации побочных продуктов (переработчики, дробилки и т. п.).

Важно: запросы здания в этом режиме **на отслеживаемый ингредиент** в цели сети не входят. Иначе утилизатор своими заказами заставит производителей делать ещё больше того, что он должен уничтожать. Запросы на прочие ингредиенты учитываются как обычно.

### 5.5. Как считать

- Список точек запроса берётся у самой сети. Свой реестр сундуков игрока вести не нужно: принадлежность к сети меняется при постройке и сносе робопортов, а запросы, заданные через логическую сеть, меняются без событий.
- Цели каждой сети пересчитываются раз в 5–10 секунд, работа размазывается по тикам.
- Скрытые сундуки мода при обходе сети пропускаются; их спрос берётся из собственного реестра мода и обновляется мгновенно, в момент выставления и снятия заказа. Иначе каждый уровень цепочки ждал бы очередного пересчёта.
- Событие ручной смены запроса помечает сеть «пересчитать вне очереди».
- После пересчёта для каждого предмета, у которого запас стал ниже цели, будятся подписанные на него спящие производители.
- Здание вне сети спит и редко перепроверяет, не появилась ли сеть.

## 6. Жизненный цикл партии

### 6.1. Принцип

У скрипта нет событий «крафт завершён» и «дрон привёз груз», поэтому здание приходится навещать. Нагрузку создаёт именно частота посещений, а не само перекладывание. Поэтому:

- скрипт загружает ингредиенты сразу на много крафтов (сколько помещается во входные слоты);
- время крафта и скорость машины известны, поэтому скрипт рассчитывает, когда порция закончится, и ставит зданию «будильник» на этот тик;
- до будильника здание не трогается.

### 6.2. Состояния

1. **Сон.** Спроса нет. Здание будит пересчёт целей сети (5.5).
2. **Заказ.** На скрытом сундуке выставлены запросы на партию. Только в этом состоянии сундук опрашивается, раз в 1–2 секунды с ростом интервала до 10 секунд. Когда партия пришла целиком, запросы снимаются. Ждать полной партии для начала работы не нужно: всё, чего хватает на целые крафты, загружается сразу.
3. **Загрузка.** Ингредиенты перекладываются из сундука в здание, сколько помещается. Будильник ставится на расчётное окончание порции.
4. **Работа.** По будильнику: отгрузить готовое (6.4), загрузить следующую порцию, дозаправить топливом, при запасе ниже порога и наличии спроса сделать дозаказ. Если спроса больше нет и ингредиенты кончились — в сон.

### 6.3. Гистерезис заказа

На здание заданы два числа в крафтах: **порог дозаказа** и **партия заказа**. Запрос выставляется, когда запас ингредиентов (сундук + здание) упал ниже порога, и равен партии за вычетом того, что уже есть. Между заказами запросы нулевые. Так дроны летают полными рейсами, а не возят по несколько предметов на каждую мелкую недостачу.

### 6.4. Пакетная отгрузка

Готовый продукт копится в выходном слоте здания. Скрипт перекладывает его в сундук снабжения, когда набралась **партия отгрузки** (задаётся по каждому продукту). Партия не может быть больше того, что вмещает выходной слот. При смене рецепта, выключении режима и сносе остаток выгружается принудительно.

### 6.5. Правило фактического состояния

Расчёт будильника — прогноз, а не гарантия. Здание может стоять без энергии, ждать внешний ингредиент, упереться в полный выход; игрок может положить предметы руками. Поэтому **при каждом пробуждении скрипт читает фактическое состояние здания и сундуков**, а не полагается на расчёт. Если ничего не изменилось, интервал до следующего пробуждения удваивается, до потолка 30 секунд.

Турели и сельскохозяйственные башни — исключение из будильника: расход патронов и момент сбора урожая непредсказуемы, поэтому они проверяются медленным опросом раз в 10–20 секунд.

### 6.6. Значения по умолчанию

| Параметр | Значение |
|---|---|
| Партия заказа | столько крафтов, сколько помещается во входные слоты здания за одну загрузку |
| Порог дозаказа | 25% партии заказа |
| Партия отгрузки | стак продукта (для предметов со стаком 1 — одна штука) |
| Партия колб | один стак |
| Партия и порог топлива | из настроек мода (раздел 8): один стак, порог 25% |
| Партия и порог патронов | из настроек мода: один стак, порог 50% |
| Партия и порог семян | один стак, порог 25% |
| Размер буфера бура | 10 слотов |

Все значения меняются в панели здания. Для топлива и патронов значения по умолчанию задаются настройками карты и меняются во время игры; изменение сразу действует на все здания, где значение не переопределено в панели. Числа в этой таблице — разумные стартовые, исполнитель может скорректировать их по результатам тестов.

## 7. Панель и отображение

### 7.1. Панель здания

Панель прикрепляется сбоку к штатному окну здания (отдельное окно не нужно). Состав зависит от типа здания:

- **Все типы:** переключатель «логистический режим», строка состояния.
- **Производящие машины:**
  - список твёрдых ингредиентов текущего рецепта, у каждого галочка «из сети»;
  - порог дозаказа и партия заказа (в крафтах);
  - список продуктов, у каждого режим (пассивный / активный / локальный) и партия отгрузки;
  - флаг «работа по избытку», выбор отслеживаемого ингредиента и порог;
  - для печей — выбор рецепта.
- **Здания с топкой:** выбор вида топлива, источник (сеть / внешний), способ доставки (строительные / логистические дроны), порог и партия.
- **Лаборатории:** партия колб.
- **Буры:** режим выхода, размер буфера.
- **Турели:** выбор вида патронов, порог и партия.
- **Сельскохозяйственная башня:** выбор вида семян, способ доставки семян, порог и партия семян, режим выхода и партия отгрузки по каждому продукту.
- **Ракетная шахта:** порог дозаказа и партия заказа.

### 7.2. Строка состояния

Игрок должен видеть, почему здание стоит. Минимальный набор состояний: «спит: нет спроса», «ждёт доставку», «работает», «стоит: выход заполнен (предмет X)», «стоит: ждёт внешний ингредиент (предмет X)», «нет логистической сети», «режим недоступен: не открыты сундуки».

### 7.3. Значок на здании

Здание в логистическом режиме помечается небольшим значком поверх спрайта. Собственной графики не делать: использовать готовые спрайты игры (например, значки логистических сундуков).

### 7.4. Чертежи и копирование

- Режим и все настройки здания сохраняются в чертеже (в тегах сущности) и восстанавливаются при постройке, в том числе дронами.
- Штатное копирование настроек (Shift + правая кнопка мыши — скопировать, Shift + левая — применить) переносит вместе с ванильными настройками и все настройки мода: режим, источники ингредиентов, пороги и партии, режимы выхода, выбранное топливо, патроны, семена и способ их доставки. Ванильное поведение копирования (рецепт и прочее) сохраняется без изменений.
- При вставке между зданиями разных типов переносится только то, что применимо к целевому зданию.
- Новое здание, поставленное вручную, по умолчанию в обычном режиме.

### 7.5. Локализация

Русский и английский.

## 8. Настройки мода

Настройки двух видов: **запуска** (меняются только с перезапуском игры) и **карты** (меняются во время игры).

### 8.1. Настройки запуска

| Настройка | По умолчанию | Действие |
|---|---|---|
| Переопределять вместимость логистических дронов | включено | Применяет три настройки ниже к логистическим дронам |
| Переопределять вместимость строительных дронов | выключено | То же для строительных |
| Базовая вместимость | 1 | Вместимость дрона без исследований |
| Множитель вместимости | 25 | Умножает и базу, и каждый бонус исследований |
| Оставить исследования вместимости | включено | Если выключено, эффект вместимости из технологий убирается |
| Логистика турелей | выключено | Включает режим для турелей |
| Логистика заправки | включено | Включает заправку топливом из сети |
| Логистика сельскохозяйственной башни | выключено | Включает режим для башни |
| Логистика ракетной шахты | выключено | Включает режим для шахты |
| Исключённые здания | пусто | Список имён сущностей, на которых режим недоступен |

### 8.2. Настройки карты (меняются во время игры)

| Настройка | По умолчанию | Действие |
|---|---|---|
| Партия топлива | 1 стак | Сколько топлива заказывать за раз |
| Порог топлива | 25% партии | Ниже какого запаса дозаказывать |
| Партия патронов | 1 стак | Сколько патронов заказывать за раз |
| Порог патронов | 50% партии | Ниже какого запаса дозаказывать |

Это значения по умолчанию для всех зданий. Здание, у которого значение переопределено в панели, использует своё. Изменение настройки подхватывается сразу, без перезапуска.

### 8.3. Вместимость дронов

Вместимость считается по формуле **(база + бонусы исследований) × множитель**. При значениях по умолчанию в ванильной игре это рост от 25 до 100: (1 + 0) × 25 в начале и (1 + 3) × 25 после всех исследований.

Требования к реализации:

- Правки делаются на последней стадии данных, по всем прототипам дронов и по всем технологиям с эффектом вместимости, без привязки к именам. Так подхватываются дроны и технологии Krastorio и других модов.
- При выключенном переопределении мод дронов не трогает вообще.
- Если после удаления эффекта технология остаётся пустой, её нужно скрыть, а зависящие от неё технологии перевесить на её предпосылки, иначе сломается дерево у других модов.
- В описании настроек указать, что база и множитель перемножаются и что дрон не несёт больше одного стака.

## 9. Жизненный цикл сущностей и сохранность предметов

### 9.1. Постройка и снос

Скрытые сундуки и запись о здании должны корректно создаваться и удаляться при всех способах появления и исчезновения здания: постройка игроком, дронами, скриптом другого мода, клонирование, снос игроком, дронами, гибель, удаление скриптом. Судя по обсуждениям существующих модов-аналогов, именно здесь у них было больше всего ошибок (пропадающие сундуки у соседних зданий, запросы, не переносящиеся при копировании).

### 9.2. Предметы не должны пропадать

- При сносе игроком или дроном содержимое скрытых сундуков возвращается вместе со зданием.
- При гибели здания содержимое высыпается на землю.
- При выключении режима содержимое сундуков переходит игроку, который выключил режим; что не поместилось, высыпается на землю.

### 9.3. Мусор

Всё, что лежит в здании и скрытом сундуке запроса и не нужно текущему рецепту, уходит через сундук активного снабжения на склад: остатки ингредиентов старого рецепта, старое топливо и патроны после смены вида, испорченные предметы, отработанное топливо.

У зданий без скрытых сундуков (турели, котлы, реакторы) мусор вывозится запросом на изъятие в призраке запроса (4.5).

### 9.4. Смена набора модов и удаление мода

- Если рецепт, предмет или сущность из настроек здания исчезли после смены модов, настройки этого здания сбрасываются без ошибки.
- Нужна консольная команда «выгрузить всё»: содержимое всех скрытых сундуков переносится в здания, а что не помещается — на землю. Её запускают перед удалением мода, иначе предметы исчезнут вместе с сундуками.

### 9.5. Мультиплеер

Всё состояние мода хранится в сохранении. Никаких данных, которые существуют только в памяти одного клиента и влияют на игру, быть не должно — иначе рассинхрон.

## 10. Производительность

Ориентир: база с 10 000 зданий в логистическом режиме не должна терять заметную долю тика на скрипт мода (цель — менее 1 мс на тик в среднем).

- Нет обхода всех зданий каждый тик. Здания навещаются по будильникам, разложенным по тикам.
- Пересчёт целей сетей и медленный опрос турелей размазываются по тикам равными порциями.
- Спящие и простаивающие здания почти ничего не стоят (рост интервала из 6.5).
- Проверка спроса делается по предметам сети, а не по зданиям.

## 11. Что проверить на прототипе в первую очередь

Эти пункты — допущения, на которых держится дизайн. Они не проверялись в игре. Начать работу нужно с их проверки на минимальном прототипе. Если допущение не подтверждается, сообщить владельцу и предложить вариант обхода, а не менять дизайн молча.

1. **Загрузка скриптом во входные слоты.** Можно ли положить ингредиенты сразу на много крафтов (до стака на слот), а не только на те два-три крафта, которыми ограничиваются манипуляторы. Если нельзя — порции будут меньше, а посещения чаще; оценить нагрузку.
2. **Цель сброса бура.** Можно ли скриптом назначить буру скрытый сундук как цель сброса. Если нельзя — рассмотреть сундук в точке сброса или скриптовый перенос.
3. **Внешние манипуляторы.** Манипулятор рядом со зданием должен работать с самим зданием, а не со скрытым сундуком внутри. Проверить на зданиях 1×1, 2×2 и 3×3.
4. **Скрытый сундук без коллизии в сети.** Он должен нормально обслуживаться дронами и входить в сеть по положению центра здания.
5. **Точки запроса сети.** Чтение списка точек запроса, их запросов, содержимого и количества «в пути»; как в списке отличить буферные сундуки от прочих; попадают ли туда персонажи и другие сущности.
6. **Событие смены запроса.** Срабатывает ли оно для сундуков (а не только для персонажей) и при правке логистической группы.
7. **Панель рядом со штатным окном.** Есть ли привязки для всех нужных типов: производящие машины, печи, лаборатории, буры, котлы, реакторы, турели.
8. **Остановка машины по выходу.** При каком заполнении выходного слота машина встаёт — от этого зависит максимальная партия отгрузки.
9. **Инвентарь испорченных ингредиентов** у машин (Space Age) и его выгрузка.
10. **Различия API между 2.0 и 2.1** для всего перечисленного выше — по официальной документации.
11. **Призрак запроса предмета.** Создание скриптом с указанием инвентаря и слота для топлива, патронов и семян; добавление строк в уже существующий призрак без потери чужих; поведение при нескольких призраках на одном здании; чтение невыполненного остатка.
12. **Запрос на изъятие** из инвентаря отработанного топлива строительными дронами.
13. **Предупреждения.** Появляется ли предупреждение о нехватке материалов, когда призрак нечем выполнить, и насколько оно навязчиво при сотнях турелей. Если это спам — предложить обход (например, создавать призрак только когда предмет есть в сети).
14. **Сельскохозяйственная башня.** Доступ к инвентарям семян и урожая, определение продукта по семени.
15. **Ракетная шахта.** Загрузка ингредиентов деталей ракеты скриптом; признак «ракета собрана, ингредиенты больше не нужны».
16. **Смена способа доставки на работающем здании.** Снятие своих строк из призрака без потери чужих; расчёт расхода топлива для будильника у зданий модов.

Результат этапа — короткий отчёт: что подтвердилось, что нет, какие обходы предлагаются.

## 12. Этапы

1. **Проверки на прототипе** (раздел 11) и отчёт.
2. **Ядро на производящих машинах:** включение режима, скрытые сундуки, жизненный цикл сущностей, цикл партии, пассивный выход, расчёт спроса.
3. **Панель:** настройки по ингредиентам и продуктам, три режима выхода, строка состояния, значок, чертежи и копирование настроек.
4. **Лаборатории и буры.**
5. **Топливо** (включая здания только с топкой) и **турели** на призраках запроса, переключатель способа доставки топлива и семян; затем **сельскохозяйственная башня** и **ракетная шахта**.
6. **Работа по избытку**, мусор, команда выгрузки.
7. **Настройки дронов.**
8. **Проверка совместимости** (Space Age, Quality, Krastorio 2, пак планет) и **релиз под 2.1**.

После каждого этапа мод должен запускаться и быть пригодным к игре в объёме сделанного.

## 13. Критерии приёмки

Мод готов, когда выполняются все сценарии:

1. **Чистая игра.** Мод запускается на Factorio 2.0 и на 2.1 без других модов и DLC.
2. **Цепочка под заказ.** Буры, печи и сборщики в логистическом режиме, без единого манипулятора. Игрок ставит буферный сундук с запросом на 200 зелёных схем — сеть производит схемы и всё, что для них нужно, и останавливается, когда запрос закрыт. Лишнего на складах не копится сверх одной партии на предмет.
3. **Полные рейсы.** При установленной вместимости дронов 100 средняя загрузка дрона между зданиями близка к партии, а не к единицам предметов.
4. **Гибрид.** Сборщик получает один ингредиент с конвейера (галочка «из сети» снята), остальные от дронов, и работает. Другой сборщик получает всё от дронов и выдаёт продукт манипулятору (локальный выход).
5. **Побочные продукты.** Рецепт с двумя продуктами не встаёт из-за побочного: тот уезжает на склад. Здание в режиме «по избытку» перерабатывает побочный продукт, когда его больше порога, и при этом не вызывает дополнительного производства этого продукта.
6. **Лаборатория** сама запрашивает колбы текущего исследования и меняет запрос при смене исследования.
7. **Топливо и турели.** Котёл и твердотопливная печь заправляются из сети выбранным топливом; отработанное топливо реактора вывозится. При включённом флаге турель пополняет выбранные патроны. По умолчанию на котлах, реакторах и турелях нет скрытых сундуков, доставку выполняют строительные дроны; нехватка топлива или патронов запускает их производство. Смена порога в настройках карты действует без перезапуска. После переключения доставки топлива на логистических дронов то же здание заправляется партиями через скрытый сундук; биокамера с высоким расходом при этом не простаивает из-за топлива. Переключение туда и обратно не теряет предметы и не создаёт двойных заказов.
8. **Башня и шахта.** При включённых флагах сельскохозяйственная башня получает выбранные семена, пока есть спрос на урожай, и отдаёт урожай в сеть; ракетная шахта получает ингредиенты деталей ракеты и перестаёт их заказывать, когда ракета собрана.
9. **Копирование.** Shift + правая кнопка на настроенном здании и Shift + левая на другом таком же переносят все настройки мода вместе с ванильными.
10. **Качество.** Сборщик с рецептом редкого качества запрашивает редкие ингредиенты; запрос «редкое и выше» закрывается любым подходящим производителем.
11. **Чертёж.** Скопированный чертежом участок базы после постройки дронами работает с теми же настройками, без ручной донастройки.
12. **Сохранность.** При сносе, гибели здания и выключении режима ни один предмет не исчезает. Скрытые сундуки не остаются «сиротами» и не пропадают у соседних зданий.
13. **Совместимость.** Игра запускается и сценарий 2 работает вместе со Space Age + Quality, с Krastorio 2 и с паком планет. Машины этих модов переключаются в режим без кода под конкретный мод. Здания модов с топкой (проверить на башнях из Cerys) заправляются при обоих способах доставки.
14. **Нагрузка.** На тестовой карте с несколькими тысячами зданий в режиме время скрипта мода укладывается в ориентир из раздела 10.
15. **Мультиплеер.** Двое игроков на одной карте, рассинхрона нет.

Записаны, чтобы архитектура им не мешала.

## 15. Тестирование

Официального тестового фреймворка у Factorio нет, но тесты трёх уровней возможны и ожидаются.

### 15.1. Юнит-тесты вне игры

Логика, которая не обращается к API игры, тестируется обычным Lua (игра использует Lua 5.2) любым привычным инструментом, например busted. Для этого код нужно строить так, чтобы расчёты были чистыми функциями, отделёнными от вызовов API:

- расчёт партии, порога и дозаказа;
- расчёт цели и запаса по набору запросов, включая условия по качеству;
- планировщик будильников и рост интервала;
- формула вместимости дронов;
- выбор механизма доставки (сундук или призрак).

### 15.2. Интеграционные тесты в игре

Тесты запускаются внутри настоящей игры в тестовом сценарии: скрипт создаёт поверхность, ставит здания, робопорты и сундуки, проматывает тики и проверяет результат. Готовые фреймворки сообщества: FactorioTest (`factorio-test`), FUnit, factestio. Выбрать тот, который работает на обеих целевых версиях игры и запускается без графики.

Так автоматизируется большая часть сценариев из раздела 13: цепочка под заказ, гибрид, побочные продукты, лаборатория, топливо, турели, качество, сохранность предметов при сносе.

### 15.3. Прогон без графики

Игра запускается из командной строки без графики на подготовленной карте и проматывает заданное число тиков (режим `--benchmark`). Это даёт:

- дымовой тест: карта загружается с модом и не падает;
- замер нагрузки для критерия 14.

### 15.4. Что автоматизируется плохо

- **Клики по интерфейсу.** Настоящий ввод сымитировать нельзя. Обработчики панели тестируются прямым вызовом с подставленными данными события.
- **Мультиплеер.** Проверяется вручную. Дополнительно стоит прогнать карту в «тяжёлом режиме» игры (`/toggle-heavy-mode`): он выявляет состояние, которое не переживает сохранение и загрузку, то есть главную причину рассинхрона.
- **Внешний вид** значков и панели — вручную.

Тесты уровней 15.1 и 15.2 должны запускаться одной командой и входить в поставку.

## Приложение. Подсказки по API

Имена приведены по памяти для версии 2.0 как отправная точка для поиска. Каждое нужно сверить с официальной документацией для 2.0 и 2.1.

- Хранение состояния: `storage`; планирование: `script.on_nth_tick`, собственная таблица «тик → список зданий».
- Отслеживание удаления сущностей: `script.register_on_object_destroyed`.
- События постройки и сноса: `on_built_entity`, `on_robot_built_entity`, `script_raised_built`, `script_raised_revive`, `on_entity_cloned`, `on_player_mined_entity`, `on_robot_mined_entity`, `on_entity_died`, `script_raised_destroy`, а также варианты для космических платформ. События сноса игроком и дроном дают буферный инвентарь, куда кладётся содержимое скрытых сундуков.
- Рецепт и качество машины: `LuaEntity.get_recipe()`; инвентари: `get_inventory(defines.inventory.*)`, `get_output_inventory()`; скорость: `crafting_speed`.
- Топка: `LuaEntity.burner` (топливный инвентарь, инвентарь отходов, допустимые категории топлива, остаток горящего топлива).
- Сеть: `LuaEntity.logistic_network`, `LuaLogisticNetwork.get_item_count`, `LuaLogisticNetwork.requester_points`, `network_id`.
- Точка запроса: `LuaLogisticPoint` (секции и слоты запросов, `targeted_items_deliver`); запросы сундука: `get_logistic_sections()`; флаг `request_from_buffers`.
- Событие смены запроса: `on_entity_logistic_slot_changed`.
- Цель сброса бура: `LuaEntity.drop_target`.
- Исследования: `LuaForce.current_research`, события начала, завершения и отмены исследования; открытость рецепта: `LuaForce.recipes[name].enabled`.
- Панель: `LuaGuiElement` с привязкой `anchor` к `defines.relative_gui_type.*`.
- Чертежи: `on_player_setup_blueprint` и теги сущностей; вставка настроек: `on_entity_settings_pasted`.
- Значок на здании: `rendering.draw_sprite` с привязкой к сущности.
- Дроны (стадия данных): `max_payload_size` у прототипов `logistic-robot` и `construction-robot`; эффект технологии `worker-robot-storage`.
- Смена модов: `script.on_configuration_changed`.
- Призрак запроса предмета: сущность `item-request-proxy` (создаётся через `create_entity` с целью и планом вставки), `LuaEntity.item_request_proxy`, поля `insert_plan` и `removal_plan` (формат `BlueprintInsertPlan`: предмет с качеством и список «инвентарь, слот, количество»).
- Настройки карты: тип `runtime-global`, событие `on_runtime_mod_setting_changed`.
- Сельскохозяйственная башня: тип сущности `agricultural-tower`; ракетная шахта: тип `rocket-silo`.
