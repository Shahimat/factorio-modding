# shm-logistic-buildings-probe

Мод-прототип программы `logistic-buildings`. Проверяет в живой игре допущения
ТЗ об игровом API — те, которые по документации не проверяются. Не
публикуется, в `mods/` не переезжает и удаляется вместе с программой
(convention `spec-program`, раздел «PoC»).

## Запуск

Прототип подключается к игре симлинком, как обычный мод, —
`docs/manuals/test-mod-locally.md`, шаг 2, только путь ведёт в `poc/`
(`FD` — каталог данных игры, там же):

```bash
ln -s "$PWD/poc/shm-logistic-buildings-probe" \
  "$FD/mods/shm-logistic-buildings-probe"
```

Дальше в игре, на любой карте:

```
/shm-probe                      список доступных проверок и строка версии
/shm-probe all                  прогон всех проверок по порядку
/shm-probe self/runtime …       прогон перечисленных проверок
```

Отчёт уходит и в чат, и в `factorio-current.log`: в чате его видно сразу, из
лога он кладётся в пруфы цели.

## Формат строки отчёта

Все проверки отвечают строками одного вида — чтобы вывод читался глазами и
разбирался в сводку одним парсером:

```
[shm-probe] <статус> | <имя> | <пояснение>
```

Поля разделены ` | `, полей всегда три, пустое пояснение превращается в `—`.
Разделитель, переводы строк и табы внутри полей гасятся: иначе строка
перестаёт разбираться.

Статусы результата:

| статус    | значение                                                      |
| --------- | ------------------------------------------------------------- |
| `ок`      | допущение подтвердилось                                       |
| `нет`     | допущение не подтвердилось, пояснение говорит, что получилось |
| `пропуск` | проверка не применима в этой сборке (например, нет Space Age) |
| `сбой`    | проверка упала с ошибкой Lua либо вернула неизвестный статус   |

Служебные строки идут в том же формате со статусами `версия` (шапка прогона),
`проверка` (строка списка) и `итог`. Итоговая строка кончается словом
`готово` — по нему видно, что прогон не оборвался на середине.

## Устройство

```
info.json          пакет прототипа: имя, версия, опциональный space-age
control.lua        точка входа: консольная команда, вывод в чат и лог
report.lua         формат строки отчёта, статусы, итог прогона
registry.lua       реестр проверок и их прогон
checks/<тема>.lua  проверки одной темы, одна тема — один файл
tests/<тема>.lua   сценарии стенда FactorioTest, npm run test:ingame
```

`report.lua` и `registry.lua` не обращаются к игровому API: прогон идёт через
переданную функцию вывода. Поэтому один и тот же реестр обслуживает и
консольную команду, и сценарий стенда.

## Стенд тестов внутри игры

Сценарии в `tests/` исполняет мод `factorio-test`, подключённый к прототипу
условным блоком в конце `control.lua`. Запуск — из корня репозитория:

```bash
npm run test:ingame              прогон headless, код возврата 1 при падении
npm run test:ingame -- -v        с подробным выводом игры
npm run test:ingame -- "печь"    фильтр по имени теста (Lua-паттерн)
```

В обычной игре стенд не участвует: без мода `factorio-test` ветка в
`control.lua` не исполняется, а `/shm-probe` работает как обычно.

## Как добавить проверки

Новый файл `checks/<тема>.lua` регистрирует свои проверки сам:

```lua
local report = require('report')
local registry = require('registry')

registry.add('тема/что-проверяем', 'что именно спрашиваем у игры', function()
  if не_получилось then
    return report.FAIL, 'что вернула игра вместо ожидаемого'
  end
  return report.OK, 'измеренное число или вердикт'
end)
```

Подключается он одной строкой в `control.lua`:

```lua
require('checks.<тема>')
```

Имя проверки — `<тема>/<что>`, без пробелов и без разделителя отчёта. Порядок
прогона — порядок регистрации.

## Проверки

| имя                 | что спрашивает у игры                                 |
| ------------------- | ----------------------------------------------------- |
| `self/runtime`      | игровой API отвечает: есть `game`, `script`, тик и моды |
| `self/report-format` | строка отчёта собирается в едином формате             |

Обе — самодиагностика каркаса: они отвечают на вопрос «оснастка вообще
работает», до того как от прототипа ждут ответов про механику. Проверки
механик приносят цели 1.3–1.6 итерации 01.

## Границы

- диалект проверяется отдельно: `npm run check-lua -- poc/shm-logistic-buildings-probe`
  (`npm run validate` в `poc/` не ходит);
- Lua 5.2, как в игре: ни `//`, ни побитовых операторов, ни `table.move`,
  ни `<const>` — convention `testing`, раздел «Диалект Lua»;
- `LICENSE`, `changelog.txt` и `thumbnail.png` прототипу не нужны и не
  заводятся.
