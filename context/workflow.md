# Протоколы взаимодействия

Сценарий определяется по ключевым словам сообщения автора. В диалоге можно
ссылаться на сценарий прямо: «работаем в `plan`».

## `plan`

Ключи: «предложи», «как лучше», «варианты», «что думаешь».

1. Загрузи релевантные entities / behaviors / conventions по namespace задачи.
2. Явно перечисли расхождения между «как есть» и «как хочу».
3. Дай 1–3 варианта решения по 2–4 строки каждый, с trade-off.
4. Одной строкой — своя рекомендация.
5. Если решение затрагивает больше одного типа изменений — предложи разбивку
   на атомарные фазы, порядок по дефолтному правилу либо с явным обоснованием
   отклонения.
6. Жди выбор. Не приступай к `execute` автоматически.

## `execute`

Ключи: «делай», «поехали», «внедряй».

1. Работаешь только после подтверждения плана и после чтения документации по
   namespace задачи.
2. Задача разбита на фазы — идёшь строго по одной фазе за раз, не смешивая
   типы изменений. В конце каждой фазы — точка согласования.
3. Между шагами — короткие статус-строки.
4. Критические алёрты — стоп, вопрос одной строкой.
5. В конце — обнови `context/views/`, затронутые `docs/behavior/*.yml`
   (`verified`) и `docs/entities/*.yml`.

## `audit`

Ключи: «проверь состояние», «где мы сейчас», «прогони проверку».

1. Пройдись по behaviors в интересующем namespace.
2. Выполни сценарии проверок, где возможно (`curl`, `grep`, локальные
   команды, запуск игры по manual).
3. Обнови `verified` и `verified_at` по факту.
4. Отчёт: сколько проверено, где расхождения с entity, где `verified: false`
   остаётся и почему.

## `challenge`

Ключи: «покритикуй», «поспорь», «найди слабое место».

1. По умолчанию не соглашайся.
2. Минимум 2 контраргумента к предложенному подходу.
3. Проверь противоречие с conventions — если есть конфликт, укажи, с какой
   именно.
4. В итоге: «ок с оговорками X» или «альтернатива Y».

## `report`

Ключи: «что сейчас активно», «где мы», «статус».

1. Не пересказывай файлы целей дословно.
2. Выдай 3–5 задач в формате
   `→ действие — [manual] → пункт X — пояснение одной строкой`.
3. Добавь блок «блокеры».
4. Одной строкой — «что делать первым».

## Атомарность фаз

Одна фаза = ровно один тип изменений по конвенции karma commit-msg: `docs`,
`fix`, `refactor`, `feat`, `test`, `perf`, `chore`, `style`. Смешивать типы в
одной фазе нельзя. Соблазн «заодно поправлю ещё вот это» — сигнал, что нужна
отдельная фаза; заметка идёт задачей в подходящую цель.

Дефолтный порядок для сложной задачи: `docs` → `fix` → `refactor` → `feat`.
Отклонения — с явным обоснованием.

Каждая фаза заканчивается точкой согласования: короткий отчёт «сделал X, готов
к фазе Y», ожидание «ок». Автоматически к следующей фазе не переходим.

Если в процессе фазы выяснилось, что документация не покрывает случай —
стоп фазу, откатить незакоммиченные изменения, инъектировать подфазу `docs`
отдельным сообщением, согласовать, и только потом вернуться к фазе заново
поверх обновлённой доки.

## Синхронизация с источниками

Ключи: «сверь всё», «синхронизируй», «обнови из источника», «проверь
источник».

Fetch — **только `curl`**, WebFetch запрещён (кэш инструмента и
pre-processing искажают контент, SHA не сойдётся):

```bash
curl -fsSL -H "Cache-Control: no-cache" -H "Pragma: no-cache" "<url>" -o "$tmp"
shasum -a 256 "$tmp" | awk '{print $1}'
```

Протокол:

1. Прочитай `sync.index_source` из `context/project.yml`. Пусто — ответь
   «источник не сохранён, пришли ссылку».
2. `curl` тянет `index.yml`, считаем SHA-256.
3. Совпал с `sync.index_sha` — «без изменений», выходим. Ни контракт, ни
   модули не тянем.
4. Не совпал — читаем индекс, для контракта из `sync.contract.key` и каждого
   `context/modules/*.yml` находим актуальный `sha256`.
5. Совпал — пропускаем; разошёлся — тянем файл, полный diff, план миграции.
6. Дополнительно: подключённый модуль пропал из индекса, или его
   `applicable_to` больше не содержит ключ базы — предупредить. Новые
   подходящие модули — упомянуть справкой, не подключать.
7. Расхождений нет — «без изменений» одной строкой.
8. Расхождения есть — единый план миграции с указанием, какие behaviors
   получат `verified: false`. Дождаться явного «да».
9. После применения обновить `sync.index_sha`, `sync.contract.synced_sha`,
   `synced_sha`/`synced_at` в manifest'ах затронутых модулей.

При тяге контракта или модуля отдельно (не через индекс) — обязательная
сверка поля `key` из frontmatter источника с сохранённым ключом. Не
совпало — стоп, не применять.

## Формат блокирующего вопроса

Одно сообщение — либо блок вопросов, либо действия по задаче. Не смешивать
«жду решения по пунктам» с «по остальным иду дальше по дефолтам».

- вопросы пронумерованы, один вопрос = одна развилка;
- у каждого явный нумерованный список вариантов (1.1, 1.2, …), не A/B/C;
- у каждого предлагаемый дефолт с обоснованием одной строкой;
- дефолт — предложение, а не принятое решение.

После отправки блока вопросов — стоп: файлы не трогаем, план не расширяем,
соседние подзадачи не подхватываем.
