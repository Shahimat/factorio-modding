# factorio-modding

Монорепозиторий модов [Factorio](https://factorio.com/) автора **Shahimat**.
Модов несколько, каждый решает свою задачу; моды могут зависеть друг от друга.

- Исходники модов — Lua, по одному пакету на мод в `mods/`.
- Инструменты сборки и публикации — TypeScript в strict-режиме, `tools/`,
  запуск через npm.
- Поддерживается только Factorio **2.1**.
- Лицензия — MIT на собственный код и ассеты, с оговоркой про ассеты Wube,
  см. [LICENSE](LICENSE).

Все моды носят авторскую приписку `shm-` во внутреннем имени —
`shm-<mod-key>`; это же префикс для имён прототипов и ключей локали.
Заголовок мода ника не несёт. Строки для игрока переводятся сразу на базовый
набор языков — convention `localization`.

## Структура

```
docs/manuals/    пошаговые ручные процедуры — для человека
docs/entities/   спецификация: что за штука, из чего состоит
docs/behavior/   ожидаемое поведение в BDD-форме с полем verified
context/         открытый слой агента: conventions, workflow, project.yml
context/index.yml ручная карта слоёв и входящих ТЗ
context/views/   YAML-очередь программ, целей и тикетов
context/main.md  рабочий handoff между сессиями
.agents/skills/  локальные инструкции агента, загружаемые по задаче
specs/           входящие ТЗ автора, по файлу на мод
plans/           согласованные планы итераций, по HTML на итерацию
mods/            пакеты модов, npm-workspaces
tools/           инструменты на TypeScript
```

Канон `docs/` читают человек и агент. Точка входа агента —
[AGENTS.md](AGENTS.md), карта — [context/index.yml](context/index.yml).
Существенные проектные правила, знания, факты и решения явно закрепляются
в канонических файлах, доступных через эту карту и переносимых с репозиторием.
Правила выбора канона — `context/conventions/project-knowledge.yml`;
документация не создаёт вторую копию значений из конфигов и схем.
Следующему участнику не нужны история прежней сессии или личная среда другого
компьютера; memory и личные заметки не являются параллельным слоем знания.
Контракт v2 не требует обязательных ролей, CLI или сборки бандлов;
синхронизация идёт по main/index upstream с SHA checkpoint в context/project.yml.
Обязательные сопровождающие skills установлены в `.agents/skills/`;
маршруты и триггеры — в `context/index.yml`. Они загружаются только по задаче,
а контроль поставки включает SHA каждого файла. Сам комплект не требует
создания manual или подключения опциональных модулей.

## Как положить ТЗ

Файл markdown прямо в `specs/`, имя любое — его задаёт автор, агент не
переименовывает. Связь ТЗ с модом агент заводит сам записью в
`context/index.yml` в секции `specs` с полем `mod_key` (та же часть, что пойдёт в имя мода
`shm-<mod-key>`); всё порождённое по ТЗ уже именуется строго по `<mod-key>`.
Дальше агент разложит ТЗ по слоям: состав мода → entity, ожидаемое поведение
→ behaviors. Работа планируется итерациями: план очередной итерации
собирается в `plans/<мод>/iter-NN.html`, согласуется с автором и только после
этого превращается в программу с целями в `context/views/`. Порядок чтения
получается прямой: `specs/` — что хочет автор, `plans/` — как мы к этому
идём, `context/views/` — что в работе сейчас.

Сам файл спеки остаётся неизменным — его правит только автор. Правила —
`context/conventions/spec-intake.yml` и `context/conventions/spec-program.yml`.
