# Верификация плана итерации

Проверь соответствие заведённых целей согласованному плану и горизонту.
Это не улучшение плана и не ревью кода.

## Границы и контекст

- Свежий независимый контекст: если сам планировал, сообщи конфликт.
  Named judge/ролевой брифинг не обязательны; helper — по workflow.
- Не меняй цели, план, код, канон и результаты проверок. Пиши только свой
  .work/plan-review/ вердикт; предыдущие раунды не перезаписывай.
- Маршрут AGENTS/project/index/workflow/project-knowledge, затем spec-program,
  consistency, engine-facts и документы итерации. Документы открыты.
- План — данность. Расхождение с ТЗ и мнение о нарезке — «замечания к плану»,
  не подмена сверки заведённых файлов.

## 1. Выбрать итерацию

Последний plans/<mod-key>/iter-NN.html; без аргумента — программа без
approved-вердикта текущей итерации. Неоднозначность — один вопрос.
Статус/дата/горизонт — meta plan-*; расхождение с видимым блоком — находка.
Нет approved плана — стоп, сообщи обход согласования, не выпускай вердикт
соответствия несуществующей согласованной версии.

## 2. Собрать заведённое

Прочитай context/views/goals.yaml, program--<mod-key>.yaml и цели текущей
итерации goal--<key>.yaml. Порядок subgoals — приоритет; depends_on — связи.
status active/planned/paused, tasks — строки priority sections;
dod/stage/plan_item/spec и способы проверки — в description.
Невыполненные критерии при заведении — норма, не требование выполнить
реализацию до проверки плана. Не требуй expect.ts, crit/todo, CLI или новую схему.

## 3. Шесть пунктов сверки

1. Состав: все цели текущей итерации, без лишних/пропущенных; вехи за
   горизонтом не стали детальными целями.
2. Критерии: plan_item указывает на существующий пункт approved плана;
   dod соответствует смыслу, обязательности и способу проверки. Есть
   тест/команда либо точный путь пруфа. Косметика допустима, подмена — нет.
3. Программа: платформа и subgoals покрывают план; финальная приёмка только
   в соответствующей итерации. Отсутствие финальной приёмки в PoC не дефект.
4. Горизонт: цели доводят ровно до состояния в шапке. В PoC есть перенос
   engine-знания в этой итерации, не обязательно отдельный в каждой цели.
   Незавершённый мод за горизонтом — норма.
5. Связи: зависимости/приоритеты прослеживаются в плане и views; платформа
   покрывает блокеры подцелей. Goal-consistency по всему множеству, без
   циклов, дублей и двух живых целей на один интент.
6. Формальные правила: минимум одна машинная проверка на цель; пруфы
   .work/proofs/<program>/<goal>/ связаны с id критериев. Границы тикетов
   понятны, непроверенное не выдано за pass. Выполни npm run check-docs,
   npm run check-secrets, проверь покрытие index и схемы views вручную.
   Непрогнанное/недоступное и старые пути checker укажи явно.

## 4. Вердикт

.work/plan-review/<mod-key>/iter-NN--verify-MM.md, MM с 01, затем последний +1.

```markdown
# Верификация плана <mod-key>, итерация NN, прогон MM

статус: changes-requested
план: plans/<mod-key>/iter-NN.html, approved <дата>
горизонт: <из шапки>
проверки: <команды, результат и ограничения>

## Сверка
1. состав — <результат>
2. критерии целей — <результат>
3. программа — <результат>
4. горизонт — <результат>
5. связи — <результат>
6. формальные правила — <результат>

## Блокирующие
1. <расхождение — файл:строка — пункт плана>

## Неблокирующие
1. <замечание — файл>

## Замечания к плану
1. <отдельное мнение или расхождение с ТЗ>
```

Approved только после всех шести пунктов, без расхождений и блокирующих.
Недостаток источников не успешная сверка. Исправляет исполнитель; повторная
проверка независимая, существенное изменение плана — новый круг согласования.

## 5. Отчёт

Три-пять строк: статус, сколько пунктов сверено, главное расхождение,
ограничения и путь вердикта. Команду открытия владельцу не навязывай.
Актуальный исход — по workflow; не выдавай ожидание исправлений за approved.
