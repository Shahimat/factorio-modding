# Ревью подцели

Проверь, закрывает ли предъявленный git index критерии цели. Это staged
review спек-программы, не plan verification и не обязательный ролевой конвейер.

## Границы и маршрут

- Свежий независимый контекст. Если писал проверяемый код — сообщи конфликт
  и остановись до решения владельца. Named judge не обязателен.
- Не меняй код, цели, план, канон/verified, git index или историю. Пиши только
  свой раунд ревью; исправления — исполнителю. Другие материалы не удаляй.
- Маршрут AGENTS/project/index/workflow/project-knowledge, затем spec-program,
  testing, consistency, secrets и документы namespace. Документы открыты;
  index ручной, bundles и ai/oc3 CLI не нужны.

## 1. Предъявленный диф

```bash
git status --short
git diff --cached --stat
git diff --cached
```

Пустой index — стоп: нечего ревьюить. Unstaged изменения не предъявлены.
Если они накладываются на staged, сообщи; машинный прогон рабочего дерева
не доказывает зелёность index. При влиянии на результат запроси чистое
предъявление, не делай stash/checkout и не меняй git-состояние сам.

## 2. Определить цель

Сначала незакрытый .work/review/<goal-key>/, затем пути дифа и границы цели,
затем context/views/goals.yaml и YAML-программа/цели. Приоритет — порядок
индекса/subgoals; состояние — status и открытые tasks, критерии — description.
Неоднозначность — один вопрос с вариантами, не ревью случайной цели.

## 3. Критерии и проверки

Собери dod из description тикетов цели и ограничения программы: id,
обязательность, kind/how, ожидаемое наблюдение, точный путь пруфа.
Сопоставь с plans/<key>/iter-NN.html §… и .work/plan-review/.
Для behavior-ссылок сравни сценарии docs/behavior с кодом; недоступный
источник — ограничение, не придуманное соответствие.

```bash
npm run check
npm run check:mod -- <mod-key>
```

Вторая команда для затронутого мода, не всего Lua-множества; платформенная
цель без мода требует scoped тестов. По каждому критерию:

- тест проверяет смысл и границы, не только форму/точный текст;
- безопасную указанную команду выполни сам, не верь отчёту исполнителя;
  внешний эффект/публикация всё равно требуют соответствующего разрешения;
- файл .work/proofs/<program>/<goal>/<id>-… существует и доказывает критерий;
  отсутствующий файл — fail, а не not-verifiable;
- not-verifiable только внешняя невозможность с явной причиной, не способ
  пропустить отсутствующий evidence;
- незавершённое не маскируется как pass; необязательное предупреждение
  не заменяет обязательный критерий. Прошлая проверка не свежая автоматически.

## 4. Что машина не ловит

Секреты/личные данные, verified:true без свежей проверки, конфликт docs/code,
критерии приняты вопреки фактам, зависимости/горизонт/порядок разошлись с
планом, решение требует журнала, противоречие conventions. Проверь реальные
пути обнаружения checker, status/description и goal-consistency; не объявляй
зелёным нулевой обход старых .oc3 путей. Stage не подменяет status.

Проверь переносимость существенного знания: AGENTS → context/index.yml →
подходящий проектный документ. Выводы должны быть доступны без истории чата,
личной среды и содержимого `.work/`; сам документ переносится с проектом,
а не исключён из него. Пруф в `.work/` может оставаться evidence, но не
единственным местом проектного знания.

## 5. Написать раунд

.work/review/<goal-key>/round-NN.md, с 01, далее последний +1.
Предыдущие раунды не перезаписывай.

```markdown
# Ревью <goal-key>, раунд NN

статус: changes-requested
диф: <файлы, объём, ограничение рабочего дерева>
проверки: <команды и результат>

## Критерии
- <id> pass — <доказательство>
- <id> fail — <что отсутствует/не соответствует>
- <id> not-verifiable — <внешняя причина>

## Блокирующие
1. <суть — файл:строка — критерий>

## Неблокирующие
1. <суть — файл>

## Ответ исполнителя
<исполнитель дописывает ответ по пунктам>
```

Approved — все обязательные критерии pass либо not-verifiable с принятой
владельцем причиной и без блокирующих; существенное знание уже разложено
в индексируемые переносимые документы. Открытое обязательное не одобряй.
Этим вердиктом не закрывай цель. Неблокирующие последнего раунда закрыты
или осознанно переведены в задачи, не потеряны.

## 6. Отчёт

Три-пять строк: статус, покрытие, главный блокер, ограничения и путь раунда.
.work автоматически не мигрирует: раунды до закрытия цели, пруфы до закрытия
программы. Перед удалением выводы переносятся в проектные слои; удаление
только после явного «да» владельца, не ревьюером. Исход — по workflow.
