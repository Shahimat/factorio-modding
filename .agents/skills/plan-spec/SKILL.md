# Планирование спеки

Планируется ближайшая итерация до мажорной неизвестности, не мод целиком.
Код и пакет мода здесь не создаются. На блокирующих вопросах и согласовании
плана — стоп; молчание не считается согласием.

## 1. Контекст и границы

Прочитай маршрут AGENTS → project/index/workflow/project-knowledge, затем
spec-intake, spec-program, engine-facts, consistency и документы namespace
спеки. Известное про движок прочитай до PoC, чтобы не повторять исследования.
Документы открыты; агент сам пишет согласованные слои и ручной индекс.
Именованные роли, ролевой брифинг, bundles и ai/oc3 CLI не обязательны.
Помощники — по триггерам и протоколу workflow, без общей области записи.

## 2. Выбрать и прочитать ТЗ

Аргумент — путь или mod_key. Без аргумента используй context/index.yml:specs
и выбери ещё не запланированное ТЗ; несколько кандидатов — один вопрос.
Спеку specs/ читай целиком и не редактируй: это авторский источник.

Есть plans/<key>/ — не начинай заново. Последняя итерация draft — продолжи
согласование; approved без целей — заведение; цели решены — следующая
итерация без повторного разбора уже разложенного ТЗ. Очередь — views/goals.yaml.

## 3. Блокирующие вопросы

Собери по workflow: противоречия ТЗ, непроверяемые требования, расхождения
с conventions/behaviors, изменения реквизитов. Если нужен выбор — question,
короткие варианты и рекомендация. После вопроса — стоп до ответа, без правок.

## 4. Разложить по слоям

Состав/зависимости/флаги → docs/entities; ожидаемое поведение → docs/behavior
со сценариями и verified:false, verified_at:null и причиной; процедуры →
docs/manuals; договорённости → context/conventions; реквизиты → project.
Следуй spec-intake, не создавай дубль существующего знания.
Сохрани ссылку spec: от корня у entity и в description программы/целей;
entity↔behavior — в обе стороны. Зарегистрируй всё в context/index.yml,
включая specs:mod_key/mod_name/path/one_liner. План опирается на записанные
слои, а не на обещанную раскладку.

## 5. План итерации

plans/<mod-key>/iter-NN.html, статус draft. Автономный HTML со стилями,
без сети; Mermaid через plans/_assets/mermaid.min.js. Если рендерера нет,
действуй по разрешениям согласованного scope, не расширяй внешние действия.
Meta plan-* и видимый блок должны совпадать; у каждой цели якорь id.
Полный формат и состав — spec-program.

- Горизонт — ближайшая неизвестность, меняющая подход/программу. Минорные
  неизвестности — допущения с условием пересмотра.
- В итерации только цели внутри горизонта: проверяемый объём на раунд ревью,
  границы, критерии и зависимости. За горизонтом — вехи одной строкой,
  без подробных целей/критериев и без файлов будущей работы.
- У каждой цели минимум одна машинная проверка. Ручные пруфы минимизируй:
  ориентир — не больше двух точек участия владельца на итерацию.
- PoC дроби по блокам механики; прототип один. Перенос подтверждённого
  engine-знания — внутри той итерации, где результат получен.
- Полную приёмку мода включай только в выводящую на неё итерацию, не в PoC.
- Сразу после введения схема порядка с кликабельными узлами; место итерации
  на общем пути и открытые вопросы.
- Пиши для человека, не внутренними ключами или ссылками на параграфы ТЗ.
  Заголовок <program-key>-<NN> - [ТЕГ] <название>, тег PoC/MVP/feat/fix;
  короткие человеческие названия целей, ключи назначаются при заведении.

## 6. Согласовать

Три-пять строк о горизонте, нарезке и участии владельца. Последняя строка
каждого сообщения с планом:

```text
open plans/<mod-key>/iter-NN.html
```

Стоп до явного «согласовано». Замечания — новый круг. Только после ответа
поставь approved и дату в meta. Новые/снятые критерии, цели и зависимости
уже approved плана снова согласуются; косметическое уточнение — нет.

## 7. Завести YAML-программу и цели

Создай только текущую итерацию: context/views/program--<mod-key>.yaml,
goal--<goal-key>.yaml; регистрация в context/views/goals.yaml с kind:program
и subgoals. Для полей, приоритетов и проверки очереди загрузи skill goals;
при создании файлов используй его references/yaml-templates.md.
Существующую программу не дублируй. status только active/planned/paused;
tasks — строки в четырёх секциях blocker/high/medium/low. Один тикет — одна
строка с результатом, итоговым типом коммита и зависимостями, не одна фаза.

В description под тикетом — проверяемые критерии dod, их id/обязательность,
kind/how, команды или точные пруфы .work/proofs/<program>/<goal>/<id>-…;
чеклист, spec: и plan_item: plans/<key>/iter-NN.html §<пункт> от корня.
stage — описание стадии/горизонта, не конкурирующий status и не новый
runtime. Платформенная работа — tasks программы; зависимости — depends_on
или явный блокер «ждёт платформу программы» согласно goals. Приоритет не
заменяет проверку зависимости. Окончательная приёмка программы — только
к стадии review, не дубликат критериев каждой цели.

Смысл и способ проверки строго сохраняют approved план. Ещё не выполненное
не получает pass. У прежней цели на ту же работу сначала согласуй перенос
критериев и истории; автоматически не удаляй и не создавай конкурирующие интенты.

## 8. Проверить и независимо верифицировать

Сверь состав, критерии, связи и дубли с планом; выполни goal-consistency,
npm run check-docs, npm run check-secrets. Убедись, что checker читает текущие
слои. Ручной context/index.yml обнови сам в согласованном scope.

Свежий независимый контекст загружает .agents/skills/verify-plan/SKILL.md,
сверяет YAML с планом без правки целей и пишет
.work/plan-review/<key>/iter-NN--verify-MM.md. Это отдельная plan verification,
не code review. Вспомогательный агент допустим, named judge не обязателен;
фон только с реальным автоматическим продолжением. Если помощник недоступен,
нужна свежая независимая сессия, а не собственный approved.
Changes-requested исправь по владельцам в согласованном scope и повтори
сверку; существенное изменение approved плана согласуй заново. До approved
цели итерации в работу не берутся.

## 9. Отчёт

Что заведено, вердикт, горизонт, первая готовая цель и почему, возможный
параллелизм, участие владельца и остаток. Не пересказывай YAML и не выдавай
незавершённую независимую проверку за одобрение. Исход — по workflow.
