# Настроить страховочный hook против записи в memory

## Когда использовать

На каждой машине, с которой ведётся работа над этим репозиторием, — один раз.
Этот manual нужен, чтобы настройку можно было воспроизвести, когда репозиторий
клонируют заново или появляется вторая машина.

На Mac автора hook **уже установлен, зарегистрирован и проверен** (2026-10-03,
матчер расширен до `Write|Edit`). Там из этого манула нужен только раздел
«Проверить, что hook работает».

## Зачем

Convention `openness` требует, чтобы устойчивые проектные факты жили в
репозитории, а не в memory агента и не в hooks. Правило мягкое и опирается на
дисциплину агента, а дисциплина сбоит: агент в отдельной сессии может записать
проектный факт себе в memory, и этот факт не увидит ни человек, ни второй
агент, ни ревьюер.

Hook — техническая страховка под это правило. Он не хранит проектных знаний,
поэтому его существование вне репозитория принципу открытости не противоречит:
само правило опубликовано в `context/conventions/openness.yml` и в контракте.

Отсутствие hook работу не блокирует.

## Как работает установленный hook

Файл: `~/.claude/hooks/block-memory-write-for-agent-operational-contract-v2.sh`

Ключ контракта берётся из **суффикса имени самого файла** — всё, что идёт
после `block-memory-write-for-` и до `.sh`. Поэтому один скрипт обслуживает
один контракт, и у автора рядом лежат такие же файлы под другие контракты
(`external-project-context-v2`, `analytical-project`).

Логика по шагам:

1. `tool_name` из payload не `Write` и не `Edit` → выход без эффекта.
2. `tool_input.file_path` не лежит под `$HOME/.claude/projects/*/memory/*` →
   выход без эффекта.
3. В `cwd` сессии нет `context/project.yml` → выход без эффекта.
4. Из `context/project.yml` читается `sync.contract.key`: через `yq`, если он
   установлен, иначе через `awk`-разбор секции `sync:` → `contract:` → `key:`.
5. Ключ не совпал с суффиксом имени файла → выход без эффекта.
6. Совпал → на stdout печатается JSON-решение
   `permissionDecision: "deny"` с пояснением, куда вынести факт. Код возврата
   при этом `0`: блокировка идёт решением в JSON, а не ненулевым exit.

Зависимость: `jq`. У автора — `/opt/homebrew/bin/jq`. Без `jq` скрипт не
работает.

Регистрация в `~/.claude/settings.json`, секция `hooks` → `PreToolUse`,
элемент с `"matcher": "Write|Edit"`, рядом с hook'ами остальных контрактов.
Матчер общий на все три скрипта в блоке, но скрипты других контрактов
проверяют только `Write` и на `Edit` молча выходят — расширение матчера их
поведение не меняет.

## Установить с нуля

1. Создай каталог, если его нет:

   ```bash
   mkdir -p ~/.claude/hooks
   ```

2. Убедись, что есть `jq`:

   ```bash
   command -v jq || brew install jq
   ```

3. Скопируй скрипт с машины, где он уже есть, либо напиши по описанию из
   раздела «Как работает установленный hook». Имя файла критично — из него
   берётся ключ контракта:

   ```
   ~/.claude/hooks/block-memory-write-for-agent-operational-contract-v2.sh
   ```

4. Сделай исполняемым:

   ```bash
   chmod +x ~/.claude/hooks/block-memory-write-for-agent-operational-contract-v2.sh
   ```

5. Зарегистрируй в `~/.claude/settings.json`. Если секция `PreToolUse` уже
   есть — добавь элемент в существующий массив, не перезаписывай его:

   ```json
   {
     "hooks": {
       "PreToolUse": [
         {
           "matcher": "Write|Edit",
           "hooks": [
             {
               "type": "command",
               "command": "/Users/<user>/.claude/hooks/block-memory-write-for-agent-operational-contract-v2.sh"
             }
           ]
         }
       ]
     }
   }
   ```

6. Прогони проверку из следующего раздела.

## Проверить, что hook работает

Пять случаев: блокировка на обоих инструментах записи, пропуск чтения,
пропуск записи в репозиторий, пропуск чужого проекта.

```bash
H=~/.claude/hooks/block-memory-write-for-agent-operational-contract-v2.sh
P="$HOME/prj/factorio-modding"
M="$HOME/.claude/projects/x/memory/y.md"

# 1 и 2. Должны вернуть JSON с permissionDecision: "deny":
printf '%s' "{\"cwd\":\"$P\",\"tool_name\":\"Write\",\"tool_input\":{\"file_path\":\"$M\"}}" | "$H"
printf '%s' "{\"cwd\":\"$P\",\"tool_name\":\"Edit\",\"tool_input\":{\"file_path\":\"$M\"}}" | "$H"

# 3. Должен промолчать — чтение memory не трогаем:
printf '%s' "{\"cwd\":\"$P\",\"tool_name\":\"Read\",\"tool_input\":{\"file_path\":\"$M\"}}" | "$H"

# 4. Должен промолчать — правка самого репозитория:
printf '%s' "{\"cwd\":\"$P\",\"tool_name\":\"Edit\",\"tool_input\":{\"file_path\":\"$P/README.md\"}}" | "$H"

# 5. Должен промолчать — CWD без context/project.yml:
printf '%s' "{\"cwd\":\"/tmp\",\"tool_name\":\"Write\",\"tool_input\":{\"file_path\":\"$M\"}}" | "$H"
```

Ожидаемо: в первых двух случаях JSON с `deny`, в остальных — пустой вывод.
Код возврата во всех случаях `0`.

## Известные ограничения

- Hook живёт вне репозитория, поэтому при клонировании на новую машину он не
  приедет — отсюда и этот manual.
- Покрыты инструменты `Write` и `Edit`. Если в Claude Code появится новый
  способ записи файлов, матчер и проверку `tool_name` в скрипте надо
  расширить.
- Механика hooks специфична для Claude Code. Для Cursor, Windsurf и прочих —
  свой аналог, если инструмент даёт механизм блокировки; иначе остаётся только
  правило `openness`.

## Если что-то пошло не так

- Hook блокирует запись в memory в других проектах → в их CWD нашёлся
  `context/project.yml` с тем же `sync.contract.key`. Это ожидаемое поведение:
  правило привязано к контракту, а не к конкретному репозиторию.
- Hook молча пропускает запись в memory в этом проекте → проверь, что сессия
  запущена из корня репозитория (hook смотрит `cwd` из payload), что
  `sync.contract.key` в `context/project.yml` не изменился, и что `jq` на
  месте.
- Формат payload и имена полей могут меняться вместе с API hooks Claude Code.
  Поэтому проверка из раздела выше — обязательная часть установки, а не опция.
